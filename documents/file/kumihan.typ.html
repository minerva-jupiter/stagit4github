    119 = 考察
    120 上記に示された例の中では，各人に指摘されるべき事項が幾つもあったことは明らかである．
    121 以下に具体的な問題点を幾つか挙げる．
    122 - 期日までに成されない仕事
    123 - 仕事の一部を他に依頼したため，その完成を待つことになった
    124 - 相談なしの仕様の変更
    125 - 不適切なワードの混入
    126 - GitHubのガイドライン違反
    127 - 曖昧な改善指示
    128 - 曖昧なPRへの指示
    129 - PRへのPRの強制マージ
    130 - ブランチルールの解除とmasterへの強制マージ
    131 - 執筆者間で持っている情報の齟齬がある
    132 - 取りまとめた後の状態を執筆者が確認しづらい
    133 - 取りまとめ側の権力乱用
    134 以上が具体的に挙げられる問題点かと思われる．
    135 これらを抽象化してまとめると以下のようになると考えた．
    136 1. ルールの不透明さ
    137 2. コミュニケーションの量の不足
    138 3. コミュニケーションの質の不足
    139 4. 役割分担の曖昧さ

    141 == ある先輩の話
    142 私が部誌について思案している話をPimではない先輩にしたところ，その部での部誌発行の際の話について伺った．
    143 曰く「執筆は希望者があつまり，word形式で提出された．編集(ここでいう取りまとめ)は名乗り出た一人が行い入稿した」ということだった．
    144 
    145 ここで，Pim Notes 2024の例と比較してみる．
    146 問題点1については，word形式というルールのみが決まっていたことになる．
    147 集まった段階で編集を名乗り出た一人が入稿を行ったので，期限などはないし，ルールに不透明さはないが監査などもない．
    148 問題点2については，そもそもコミュニケーションの必要性がない．ルールの周知さえされていればよかったので，コミュニケーションの量の不足は問題ではない．
    149 問題点3についても，2と同様と考える．
    150 問題点4については，役割がきちんと分担されていることは明らかである．
    151 
    152 つまり，手っ取り早い策としては，一人が取りまとめを担当し，全権を移譲すればよいということになる．
    153 しかしこれは，取りまとめる一人が優秀である必要がある．
    154 やろうと思えば，レビューを通していない不適切な文章を含めて入稿することもできてしまう．
    155 
    156 また，規模が大きくなるほど編集者の負担が大きくなるため，この方式を広く導入することは難しいと考えられる．
    157 
    158 なので，これらに変わる技術系同人誌取りまとめに関する方策を検討したい．
    159 先に上げた問題点と品質管理を考慮し，方策に必要な要請を以下に示す．
    160 1. 執筆側に示すルールを明文化し広報すること
    161 2. コミュニケーションなしに全体へ影響する変更ができないこと
    162 3. 各人の役割を分担し，責任の分岐をすること
    163 4. 品質についてレビューする機構を設け，これをスルーしての出版社への入稿を禁止すること
    164 以上を満たす方策が必要なのではないかと考えた．
    165 
    166 == ルール
    167 ここで私が提案したい方策を述べる．
    168 銘打った通り「ルール」である．
    169 ここでいう「ルール」とは編集側から執筆側に提示されるルールのことではなく，合同誌の編集側と執筆側の双方が守るべき規則である．
    170 ルールには以下のことが記載されたい．
    171 - 行為(掲示・脱入稿・編集等)には行為者以外の承認者を設け，権限を付与すること
    172 - 必要な事項は編集側から執筆側全員に掲示され，編集者が執筆者を兼任する際も，掲示されていない情報を使用しないこと
    173 - 役割の分担と共に，権限と責任の分岐点を定めること
    174 - 申し立てや意見は双方合意を原則とし，やむを得ない場合は権限と責任を有する側が決定すること
    175 
    176 == ツールについて
    177 ルール通りの運用について，助力となるツールの存在を周知されたい．
    178 大きな軸であるのがGitHubである．
    179 適切な権限設定と，ブランチルールを施せば，行為の承認と実行のフローがスムーズになることが期待される．
    180 しかし，Pim Notes 2024では，ブランチルールで保護されていないPRのブランチが強制的にマージされるということが起きた．
    181 このようなことを防ぐ方法はGitHub上には用意されていない(または難しい)ようである．
    182 完全にツールに任せるのではなく，ルールに追記するなどして，適切な運用を探るべきである．
    183 
    184 また，環境ごとにビルド環境が異なる組版システム(ローカルコンパイルのLaTeX)などは，執筆側にとっても編集側にとっても難しい．
    185 そのため適宜GitHub Actionsを用いて自動コンパイルを実施するなどの工夫が求められる．
