      8 # Package Pinning
      9 
     10 For [#476](https://github.com/microsoft/winget-cli/issues/476)
     11 
     12 ## Abstract
     13 
     14 This spec describes the functionality and high level implementation design of Package Pinning feature.
     15 
     16 ## Inspiration
     17 
     18 This is inspired by functionalities in other package managers, as well as community feedback.
     19 - Packages may introduce breaking changes that users may not want integrate into their workflow quite yet.
     20 - Packages may update themselves so that it will be duplicate effort for winget to try to update them.
     21 - User may want to maintain some of the packages through other channels outside of winget, or prefer one source over others within winget.
     22 - User may want some of the packages to stay in some major versions but allow minor version changes during upgrade.
     23 
     24 ## Solution Design
     25 
     26 #### Package Pinning types
     27 To achieve goals listed above, winget will support 3 types of Package Pinning:
     28 - **Blocking:** The package is blocked from `winget upgrade --all` or `winget upgrade <specific package>`, user has to unblock the package to let winget perform upgrade.
     29 - **Pinning:** The package is excluded from `winget upgrade --all` but allowed in `winget upgrade <specific package>`, a new argument `--include-pinned` will be introduced to let `winget upgrade --all` to include pinned packages.
     30 - **Gating:** The package is pinned to specific version(s). For example, if a package is pinned to version `1.2.*`, any version between `1.2.0` to `1.2.<anything>` is considered valid.
     31 
     32 To allow user override, `--force` can be used with `winget upgrade <specific package>` to override some of the pinning created above.
     33 
     34 #### Package Pinning Configuration Storage
     35 
     36 A separate sqlite db (other than the existing tracking catalog) will be created to store the package pinning configurations from user.
     37 ```text
     38 PackageIdentifier       SourceIdentifier       Version        PinningType
     39 ----------------------------------------------------------------------------
     40 Microsoft.TestApp       winget                 1.2.*          Gating
     41 ```
     42 
     43 **Notes:** For this iteration, winget will only support pinning packages that are locally installed and correlatable with at least one of the remote sources. Winget will record a pinned package by the PackageIdentifier and SourceIdentifier. There can only be one pinning configuration for a specific package. In the future, winget may consider pinning packages from installed packages (upon improving the installed package's PackageIdentifier logic).
     44 
     45 ## UI/UX Design
     46 
     47 #### winget pin commands
     48 
     49 A new `winget pin` command with 3 sub-commands will be introduced.
     50 - Add package pinning configuration:
     51 
     52   `winget pin add <package> [--version <optional gated version>] [--source <source>] [--force] [--blocking]`
     53 
     54 - Remove package pinning configuration:
     55 
     56   `winget pin remove <package> [--source <source>] [--force]`
     57 
     58 - List package pinning configuration:
     59 
     60   `winget pin list <package> [--source <source>]` for a specific package or `winget pin list` to list all
     61 
     62 #### Blocking
     63 To block a package from upgrade, use `winget pin add <package> --blocking`
     64 ```text
     65 cmd> winget pin Microsoft.TestApp --blocking
     66 ```
     67 Now the pinning configuration is recorded as
     68 ```text
     69 PackageIdentifier       SourceIdentifier       Version        PinningType
     70 ----------------------------------------------------------------------------
     71 Microsoft.TestApp       winget                                Blocking
     72 Microsoft.TestAppStore  msstore                               Blocking
     73 ```
     74 **Note:** by default packages correlated from all sources are blocked, user can pass in `--source` to block for a specific source
     75 
     76 Corresponding upgrade behavior
     77 ```text
     78 cmd> winget upgrade -all
     79 Microsoft TestApp is blocked from upgrade and skipped
     80 
     81 cmd> winget upgrade Microsoft.TestApp
     82 Microsoft TestApp is blocked from upgrade
     83 
     84 cmd> winget upgrade Microsoft.TestApp --force
     85 Success
     86 ```
     87 
     88 #### Pinning
     89 To pin a package from `winget upgrade --all`, use `winget pin add <package>`
     90 ```text
     91 cmd> winget pin Microsoft.TestApp
     92 ```
     93 Now the pinning configuration is recorded as
     94 ```text
     95 PackageIdentifier       SourceIdentifier       Version        PinningType
     96 ----------------------------------------------------------------------------
     97 Microsoft.TestApp       winget                                Pinning
     98 Microsoft.TestAppStore  msstore                               Pinning
     99 ```
    100 **Note:** by default packages correlated from all sources are pinned, user can pass in `--source` to pin for a specific source
    101 
    102 Corresponding upgrade behavior
    103 ```text
    104 cmd> winget upgrade -all
    105 Microsoft TestApp is pinned from upgrade and skipped
    106 
    107 cmd> winget upgrade Microsoft.TestApp
    108 Success
    109 ```
    110 
    111 #### Gating
    112 To gate a package to some specific version, use `winget pin add <package> --version <gated version>`
    113 ```text
    114 cmd> winget pin Microsoft.TestApp --version 1.2.*
    115 ```
    116 Now the pinning configuration is recorded as
    117 ```text
    118 PackageIdentifier       SourceIdentifier       Version        PinningType
    119 ----------------------------------------------------------------------------
    120 Microsoft.TestApp       winget                 1.2.*          Gating
    121 Microsoft.TestAppStore  msstore                1.2.*          Gating
    122 ```
    123 **Note:** by default packages correlated from all sources are gated, user can pass in `--source` to gate for a specific source
    124 
    125 Corresponding upgrade behavior
    126 ```text
    127 cmd> winget upgrade -all
    128 Success  // If the available versions for upgrade are: 1.2.3 and 1.3.0, the selected version for upgrade is 1.2.3
    129 
    130 cmd> winget upgrade Microsoft.TestApp
    131 Success  // If the available versions for upgrade are: 1.2.3 and 1.3.0, the selected version for upgrade is 1.2.3
    132 
    133 cmd> winget upgrade Microsoft.TestApp --version 1.3.0
    134 Microsoft TestApp is gated to version 1.2.* Override with --force
    135 
    136 cmd> winget upgrade Microsoft.TestApp --version 1.3.0 --force
    137 Success
    138 ```
    139 
    140 **Note:** Regarding gated version syntax, it will be mostly same as what current winget version supports, except with special `.*` in the end as wild card matching any remaining version parts if there are any.
    141 
    142 Example:
    143 When `.*` in the end is detected:
    144 Gate version `1.0.*` matches Version `1.0.1`
    145 Gate version `1.0.*` matches Version `1.0`
    146 Gate version `1.0.*` matches Version `1`
    147 Gate version `1.0.*` matches Version `1.0.alpha`
    148 Gate version `1.0.*` matches Version `1.0.1.2.3`
    149 Gate version `1.0.*` matches Version `1.0.*`
    150 Gate version `1.0.*` does not match Version `1.1.1`
    151 
    152 In rare cases where `*` is actually part of a version, only the last `.*` is considered wild card:
    153 Gate version `1.*.*` matches Version `1.*.1`
    154 Gate version `1.*.*` matches Version `1.*.*`
    155 Gate version `1.*.*` does not match Version `1.1.1`
    156 
    157 If no `.*` in the end is detected, the gate version gates to the specific version:
    158 Gate version `1.0.1` matches Version `1.0.1`
    159 Gate version `1.0.1` does not match Version `1.1.1`

    161 ## Capabilities
    162 
    163 ### Accessibility
    164 
    165 Accessibility should not be impacted by this change. There will be a few more tables printed to the terminal in certain cases, but they should use the current table implementation used by `winget upgrade` and `winget list`.
    166 
    167 ### Security
    168 
    169 Security of the Windows Package Manager should not be impacted by this change. However, security of user's software may be, as if they pin a insecure version of a package, it will not be upgraded by Winget unless explicitly requested by user.
    170 
    171 ### Reliability
    172 
    173 The change will improve reliability, as users will be able to have fine-grained control of the Windows Package Manager's upgrade functionality to ensure their workflow is not disrupted.
    174 
    175 ### Compatibility
    176 
    177 There should not be any breaking changes to the code. Although there could be a mild breaking change to the behavior of `upgrade --all` (not all packages are upgraded anymore since pinned ones are skipped), this is purely opt-in from the user's perspective at this time (if they do not pin software, there should not be a change).
    178 
    179 ### Performance, Power, and Efficiency
    180 
    181 There should not be any notable performance changes.
    182 
    183 ## Potential Issues
    184 
    185 - Installation/Upgrades from Com Apis may be impacted by user's package pinning configuration. It could be mitigated by returning a specific error code and the caller  retrying with Force option.
    186 - Package dependencies resolution may be impacted by user's package pinning configuration.
    187 - Package imports may be impacted by user's package pinning configuration.
    188 
    189 ## Future considerations
    190 
    191 - Implementation in this spec only supports pinning from remote sources, so all installed versions from same package share the same pinning configuration. Winget could better support side by side installations by introducing package pinning from installed source.
    192 - Package pinning from user and from manifest are stored separately, we may integrate the `winget pin` commands to control package pinning from manifests.
    193 - A couple UI integrations can be made to `winget upgrade` and `winget list` to show pinned status during listing.
    194 - Dependencies flow can be improved to first check pinned status of each dependent package before trying to install all dependencies.
    195 - Support setting pinned state right after installation/upgrades like `winget install foo --pin`.
    196 - Improvements to import export commands to work seamlessly with existing package pinning configurations.
