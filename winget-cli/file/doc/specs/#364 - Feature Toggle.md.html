      8 # Feature Toggle
      9 
     10 For [#364](https://github.com/microsoft/winget-cli/issues/364)
     11 
     12 ## Abstract
     13 
     14 As features are implemented within winget, they may cause disruption to users oblivious to the fact that they are in progress. In order to allow work to be done in master, and distributed to early adopters for their feedback, this spec suggests that settings should be used to control "experimental" features. We use this term [as others have](https://github.com/PowerShell/PowerShell-RFC/blob/master/Final/RFC0029-Support-Experimental-Features.md) to mean work in progress that is not yet ready for release to the general audience.
     15 
     16 ## Inspiration
     17 
     18 We realize that we need to be able to:
     19 1. deliver work in progress to users so that we can receive feedback
     20 2. work in master without creating multiple, divergent branches
     21 3. not disrupt users who do not wish to investigate unfinished features
     22 
     23 Thank you to @megamorf for the link to the PowerShell Experimental Features RFC.
     24 
     25 ## Solution Design
     26 
     27 A new settings block will be added to the settings file for experimental features to be toggled. By default, all experimental features will be disabled.
     28 
     29 A hidden command will be added to the root:
     30 ```
     31 >winget features
     32 The following experimental features are in progress.
     33 They can be configured through the settings file (winget settings).
     34 
     35 Feature  Status   Link
     36 --------------------------------------------------------------------
     37 Example1 Enabled  https://github.com/microsoft/winget-cli/issues/364
     38 Example2 Disabled https://github.com/microsoft/winget-cli/issues/396
     39 ```
     40 When run, this command will give the status of each feature (enabled/disabled), as well as a link to the Issue or Spec.
     41 
     42 Internally, a single flag enum will be used to reference experimental features. All command line parsing objects will have a field added for the feature(s) to which they belong. Any internal behavioral changes will be made based on a check using this enum. In this way, transitioning a feature either to release or remove can be done by finding by a single identifier.
     43 
     44 A feature is released by removing the feature enum value in code, and all related references. The value in settings will become ignored, and we can keep a list in a comment to prevent future reuse of settings names.
     45 
     46 ## Settings File
     47 
     48 To enable experimental features a user will need to modify the settings file. The settings file can be opened via the settings command.
     49 
     50 ```
     51   "experimentalFeatures": {
     52       "example1": true,
     53       "example2": false,
     54       "example3": true
     55   }
     56 ```
     57 
     58 ## UI/UX Design
     59 
     60 Experimental features can impact the winget user interface in 2 ways; new commands and options. Both will be added to the parse tree, but hidden from help view if disabled. When enabled, they will be labeled as experimental to reiterate this to the user. If a user attempts to use an experimental command or option that is not enabled, a special error will be presented to indicate that this feature is experimental and must be enabled via settings.
     61 
     62 If the feature needs settings after release, they should be added as part of the feature work, and can be tagged with the enum value as well.
     63 
     64 ## Capabilities
     65 
     66 
     67 
     68 ### Accessibility
     69 
     70 This should have no direct impact on accessibility.
     71 
     72 ### Security
     73 
     74 There should be no security impact directly, although we must remember that any medium IL process will be able to enable any feature by writing to the settings file. But any experimental feature should be created with the intention of becoming released, and so should have its own security consideration.
     75 
     76 ### Reliability
     77 
     78 One of the goals is to increase reliability for unaware users, so that they do not accidentally stumble into an incomplete feature.
     79 
     80 ### Compatibility
     81 
     82 No breaking changes to existing behavior.
