      8 # Package matching bug fix
      9 
     10 For [#292](https://github.com/microsoft/winget-cli/issues/292)
     11 
     12 ## Abstract
     13 
     14 The winget.exe client attempts to be generous with the `search` command, but is a bit too generous with `install`. The *id*
     15 should be the unique key to identifying a package (other than the package version). It should also be case-insensitive from the perspective of command execution, but it should be case-sensitive in terms of the displayed value.
     16 
     17 If a manifest was created with the *id* "Git.Git" then that is what would be displayed in the client output.
     18 Any combination of case in the `install` command should match.
     19 
     20 If multiple versions of the package have been created, and they differ in the casing for the *id* then the most recent version
     21 of the manifest should be used for displaying the characters in the search output.
     22 
     23 The latest version of a package is also the version that should be displayed during `search`, and subsequently installed.
     24 
     25 ## Inspiration
     26 
     27 `winget install git.git` should work.
     28 
     29 ## Solution Design
     30 
     31 Installing a package by using the *Id* as the package name should not require disambiguation.
     32 The package *Id* should perform a case-insensitive match. If the given *Id* is exact, it should not
     33 be confused with a longer *Id*
     34 `winget install git.git` should install that package
     35 The `git.gitLFS` should not cause ambiguity
     36 
     37 If the value passed as a package *Id* is a substring, or there is still ambiguity, the help text should provide an example.
     38 
     39 ## UI/UX Design
     40 
     41 Executing `winget install git.git` will install the Git package.
     42 Executing `winget install git.g` will provide additional guidance:
     43 Multiple apps found matching input criteria. Please refine the input.
     44 Try providing the Id: winget install git.git
     45 
     46 For the example above, the help could default to the Id for the top listed package from the search result.
     47 
     48 ## Capabilities
     49 
     50 This should help reduce the friction for users trying to install a package when there is ambiguity.

     70 ## Potential Issues
     71 
     72 Users may not realize another package exists with a longer name, and may install a program other than what they intended.
     73 If "git.git" and "git.gity" both existed and the user were to press enter before typing the final "y", the git.git package would
     74 be installed rather than what they intended.
     75 
     76 ## Future considerations
     77 
     78 There are changes to how results should displayed to reduce the likelihood of a user mistakenly assuming the "Name" is a key value
     79 for a package. The client commands should be case-insensitive, but the display should still be case-sensitive to support ease of
     80 reading. Long names can be easier to understand when presented in camel case, pascal case, or with a branded letter casing.
     81 The client also needs a mechanism to display all of the available versions of a package.
